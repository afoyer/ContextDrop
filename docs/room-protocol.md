# Room protocol and extension order

Room protocol version 4 uses an installation-stable member ID, a display name, and an operation ID. A guest submits a change without applying it. The host validates it, applies it once, and echoes the accepted change to every member, including the sender. A refusal carries the operation ID and reason. The host's acceptance order resolves card text, collapse, and position conflicts; those fields have no client timestamps. A guest drags at its local position immediately and sends throttled updates. Chat and card inputs show a pending state; after five seconds they report that the host has not replied, keep the input saved, and prevent another submission until acceptance or rejection. A rejected edit stays editable. A draft from a removed chat can be restored into the room's ask bar.

The host's admission ledger caches each tile's encoded size and re-encodes only the changed tile. Normal growth stops at 12 MiB, leaving headroom below the 16 MiB wire limit for snapshot framing and terminal status. A refused streamed delta stops its owner's reply task. This is an admission rule, not a measured Multipeer performance claim: before distributing builds, test joining a room near the ceiling on two Macs, including a Bluetooth path, and lower the budget if joining is unacceptably slow. Raising a low budget later is safer than lowering one after rooms rely on it.

Delivery order for follow-up work:

1. Finish and test protocol version 4 on two Macs. Pause parallel room features while its post paths and wire format change. Test two people with the same display name, guest acceptance and refusal, a slow reply, reconnect/version mismatch, stream budget refusal, and a near-ceiling join.
2. Extend provider support through `ChatProvider`, `RunHandle`, and `ProviderKind.capabilities`. Keep CLI-specific permission/question encoding in each adapter. Route room answers through `RoomAnswerProvider`. Keep one run generation per conversation so late events from a cancelled provider cannot change a replacement run.
3. Add connectors and new tile types only when a feature needs them. Connector content must be marked untrusted at ingestion, delimited when passed to a provider, and never treated as instructions. A coding run that includes imported, shared, or room-supplied content is capped at **Ask before editing** for that answer and subsequent answers in the same conversation, even if its selected level is higher. The user can still approve individual requests. Credentials stay on the owner's Mac. Review connector-specific sharing and retention before exposing it in a room.

There is no undo yet: removing a tile remains final. A future operation log should record accepted and rejected operation IDs, member IDs, change kind, time, and refusal reason in bounded local storage, without message text, file bytes, or secrets. It will make two-Mac diagnostics easier without turning the room into an event-sourced database.
